## 0. How to read this document

This plan is **grounded against the current `main` codebase** (verified 2026-05-19, commit
`d28c4de`), not just against the spec. Where the spec's assumptions diverge from reality, this
plan follows reality and flags the gap. Three decisions taken before drafting:

| Decision | Choice | Effect |
|----------|--------|--------|
| Deliverable now | Plan only | Implementation starts after review |
| Runbook trigger scope (Sprint 3) | **Build the watcher-evaluation loop too** | New subsystem; see §6 Sprint 3 |
| Role naming | **Rename `monitor` → `probe`** | Disambiguates role vs. cron subsystem in logs (spec Open Q5) |

> **Naming note:** The spec uses `'monitor'` for the cron observation role and acceptance
> criteria G1–G11 refer to it. Throughout this plan the role is `'probe'`. All AC references
> below substitute `probe` for `monitor`; behaviour is otherwise identical.

### 1.1 The one gap: no watcher-firing path exists

The spec §13.6 frames runbook triggering as *extending* an existing "watcher fires → LLM session"
path. **That path does not exist.** `watcher-register` stores watcher definitions in
`watcher-registry`, but nothing evaluates watchers on a cron tick or fires a session/runbook when
one triggers. There is also **no `runbook_name` field** on the watcher schema.

Consequence: per the decision above, Sprint 3 must **build** the watcher-evaluation loop, not
extend it. This is scoped explicitly in §6.

## 2. Target architecture

```
Operator email
      │
      ▼
Intent Classifier (Haiku, regex fast-path first, no tools)
      │
      ├─ 'query'           ─► Query Agent  (Sonnet, read-only tools)
      └─ 'command'/'ambiguous' ─► Action Agent (Sonnet, full tool set)

Cron probe tasks  ─► Probe Agent  (Haiku, read-only tools; writes ASM)
Cron Monday 08:00 ─► Audit Agent  (Haiku, session-store read tools)

Watcher-eval tick (NEW) ─► watcher triggers
      │
      ├─ has runbook_name + runbook exists ─► Runbook Executor (deterministic, no LLM)
      └─ otherwise                          ─► Probe Agent LLM session
```

Shared blackboard is `session.db` (per spec §4 table) — no message bus, no parallelism, no
LLM-authored runbooks (all spec Non-Goals retained).

### 2.1 The four roles

| Role | trigger.type | model | maxTokens | maxIter | tool risk set |
|------|-------------|-------|-----------|---------|---------------|
| `probe` | `cron` | Haiku | 2048 | 20 | `['read']` |
| `query` | `email` | Sonnet | 8192 | 20 | `['read']` *(see §3.1 — `dynamic` excluded)* |
| `action` | `email` | Sonnet | 8192 | 20 | `['read','medium','high','critical','dynamic']` |
| `audit` | `cron` | Haiku | 4096 | 10 | `['read']` |

## 3. Resolved open questions

The spec ends with 5 open questions. Resolutions adopted by this plan:

| # | Question | Resolution |
|---|----------|------------|
| Q1 | Ambiguous intent → Action Agent or clarification round-trip? | **Route ambiguous → Action Agent.** It can read state and ask for clarification naturally; no extra round-trip. (Spec's own recommendation.) |
| Q2 | Query Agent calling `appliance_api_call` (dynamic, POST→high)? | **Exclude `dynamic` from the Query Agent risk set** → `query: ['read']`. Prevents a read session from triggering an action-approval email (the leak the spec worried about). This is the one deliberate deviation from the spec's `query: ['read','dynamic']`. |
| Q3 | Runbook approval for non-read steps? | **Option (a): non-read runbook steps require `auto_approved: true`** at authoring time. Avoids stalling a cron thread on an email-approval wait. Async approval-and-wait deferred. |
| Q4 | Audit report only on anomalies? | **Always send weekly.** A weekly "all clear" is a liveness signal. |
| Q5 | Rename `monitor` role? | **Renamed to `probe`** (decided up front). |

## 4. Risk register

| Risk | Severity | Mitigation |
|------|----------|------------|
| `getSchemas(role)` change silently narrows tools for an existing caller | High | Keep `getSchemas()` (no arg) returning all tools — backward compatible. Only role-aware callers pass a role. (Spec §8.) |
| Role-keyed Layer 0 changes the cached prompt block per role | Medium | Intended — each role is a distinct persona. Verify cache key still stable *within* a role across turns; add a context-builder test asserting Layer 0 == `COSA_IDENTITY_BY_ROLE[role]`. |
| Watcher-eval loop (new) fires runbooks/sessions unexpectedly in prod | High | Ship behind a config flag (`appliance.watchers.evaluation_enabled`, default off until soaked); dry-run logging mode first. |
| Runbook executes destructive tools deterministically with no human in loop | High | `auto_approved` defaults to `0`; non-read steps blocked unless explicitly authored as auto-approved; `max_iterations` guard; failure → operator alert. |
| Intent misclassification routes a command to read-only Query Agent | Medium | Query Agent identity instructs it to tell the operator to resubmit as a command; ambiguous defaults to Action. G2 ≥90% gate on 30-email harness. |
| Migration applied to live `session.db` on deploy | Medium | Column-add form is idempotent + guarded; runs inside the existing migration transaction; no table rebuild. |
| Two new tables share `session.db` lifecycle | Low | Mirror ASM: same `getDb()`, migrations run at boot before tool registration. |

## 6. Implementation path

Each sprint ends green (`npm test`) and is independently mergeable to `2.0`. Estimated effort
in working-days; sequencing is strict (Sprint 1 is foundational for all others).

### Sprint 1 — Role infrastructure (~3 days) → G1–G5, G11

Order matters: bottom-up so each layer compiles against the one below.

1. **`src/session-store.js`** — add two guarded column migrations (`agent_role TEXT`,
   `intent_raw TEXT`) following the existing `PRAGMA table_info` guard pattern. Extend
   `createSession(sessionId, trigger, opts)` to persist `agentRole`/`intentRaw`. *Backward
   compatible: opts optional.*
2. **`src/tool-registry.js`** — add `ROLE_PERMITTED_RISK` constant (exported) and
   `getSchemas(role?)`. No-arg call unchanged (returns all). Add registry tests for each role's
   filter (G3).
3. **`src/context-builder.js`** — add `COSA_IDENTITY_BY_ROLE` map (4 personas from spec §6.2,
   `monitor`→`probe`). `build({…, role})` selects Layer 0 by role (fallback to `COSA_IDENTITY`);
   `buildToolsSection(role)` → `getSchemas(role)`.
4. **`src/orchestrator.js`** — `runSession(trigger, options = {})`. Add `deriveRole(trigger,
   options)` (`cron`→`probe`, email→`action` default). Replace `isCron` ternaries with
   `MODEL_BY_ROLE` / `MAX_TOKENS_BY_ROLE` / `MAX_ITER_BY_ROLE`. Pass `role` to context-builder
   and `getSchemas`. Persist role+intentRaw via `createSession`.
5. **`src/intent-classifier.js`** (NEW) — `classify(emailText) → {intent, confidence, raw}`.
   Regex fast-path (spec §5.3) → single Haiku call (`max_tokens:64`, JSON-only) → fallback
   `'ambiguous'` on any failure.
6. **`src/main.js`** — email handler classifies, maps `query→query` else `action`, passes
   `{role, intentRaw}` to `runSession`.

**Sprint 1 tests:** session-store migration + createSession; tool-registry role filters (G3);
context-builder role→Layer0/tools; orchestrator role derivation + model selection; classifier
regex/JSON/fallback unit tests.

### Sprint 2 — Audit Agent (~1 day) → G6

1. **`src/cron-scheduler.js`** — `runAuditAgentTask()`: `runSession({type:'cron',
   source:'audit-agent', message}, {role:'audit'})`, then `emailGateway.sendEmail(...)` with the
   report. Schedule `0 8 * * 1` (Mon 08:00). Add to `_taskRunnerMap()`.
2. Ensure the audit role's read tool set includes whatever session-history read tool the report
   needs (`session_search`/`db_query` read path) — **audit blocker check below.**
3. **`src/main.js`** — nothing new beyond cron registration (handled in scheduler `start()`).

> **Sprint 2 prerequisite to verify:** the spec assumes read tools `session_search` and a
> read-only `db_query` exist for the Audit Agent to aggregate `tool_calls`/`approvals`. **These
> were not confirmed present** in the verification pass. First task of Sprint 2 is to confirm or
> build a read-only session/telemetry query tool; if absent, that becomes a small sub-task
> (`src/tools/session-query.js`, `riskLevel:'read'`). This is the most likely scope surprise.

### Sprint 3 — Runbook system + watcher-evaluation loop (~4 days, was 3) → G7–G10

Expanded from the spec because the watcher-firing path must be built, not extended.

1. **`src/runbook-store.js`** (NEW) — mirror `appliance-state-machine.js`: `runMigrations()` over
   a `RUNBOOK_MIGRATIONS` array creating `runbooks` + `runbook_runs` (+ indices) per spec §13.2,
   sharing `session.db`. API: `upsert/get/list/delete/logRun/updateRun`.
2. **`src/runbook-executor.js`** (NEW) — `executeRunbook(name, triggerCtx)`: step loop via
   `toolRegistry.dispatch()`, `resolveDotPath()` convergence check, `max_iterations` guard,
   `on_failure` handling, failure alert email. Enforce **non-read steps require
   `auto_approved`** (Q3 resolution) — reject/skip otherwise with a logged abort.
3. **`src/tools/runbook-upsert.js`** (`medium`, action), **`runbook-list.js`** (`read`;
   query+action+audit), **`runbook-trigger.js`** (`high`, action).
4. **Watcher-evaluation loop (NEW subsystem):**
   - Add optional `runbook_name` to the `watcher-register` tool schema and watcher-registry record.
   - New cron task `runWatcherEvalTask()` on a tick (e.g. `*/5 * * * *`): evaluate each enabled
     watcher against current appliance state; on trigger, if `runbook_name` set and runbook
     exists → `runbookExecutor.executeRunbook(...)`, else → `runSession({type:'cron',
     source:'watcher'}, {role:'probe'})`.
   - **Gate behind `appliance.watchers.evaluation_enabled` (default false)** + dry-run log mode
     for first soak. Register in `_taskRunnerMap()` and `start()`.
5. **`src/main.js`** — register the three runbook tools.
6. **Tests:** `runbook-store.test.js`, `runbook-executor.test.js` (convergence success/fail,
   abort, max-iter, auto_approved gating), watcher-eval dispatch test.

### Sprint 4 — Hardening (~2 days) → G2 (full), G3/G4 integration

1. **`tests/intent-classifier.test.js`** — 30 synthetic emails (5 categories × 6); assert ≥90%
   correct routing (G2).
2. Integration test: email → classify → route → role-correct tool set (G3/G4).
3. Runbook `auto_approved:false` path test — non-read step blocked from deterministic execution.
4. Audit Agent report test with seeded session data.

## 8. Data model changes

```
sessions   + agent_role TEXT   ('probe'|'query'|'action'|'audit')
           + intent_raw TEXT    (classifier JSON; null for cron)

runbooks       (NEW)  id, name UNIQUE, description, steps(JSON),
                      convergence(JSON|null), max_iterations, on_failure,
                      auto_approved, version, created_at, updated_at
runbook_runs   (NEW)  id, runbook_name, trigger_ctx(JSON), steps_log(JSON),
                      converged(0|1|null), iterations, outcome, started_at, finished_at
```

No other existing table changes.

## 9. Sequencing & merge strategy

- Work proceeds on `2.0`; each sprint is a self-contained set of commits ending green.
- `G11` (no regression) is enforced by running the full suite at the end of every sprint.
- Recommend a checkpoint review after **Sprint 1** (the foundational, highest-blast-radius
  change) before proceeding to 2–4.
- The watcher-eval loop (Sprint 3) ships **disabled by default**; enabling it in production is a
  separate, deliberate operator action after a soak.
